- **pgw#1313 (COMPATIBILITY program, 1 of 9): ONE requirement vocabulary,
  `{minimum, recommended}` over one term bag, at THREE declaration scopes.**
  Charter: Paul, 2026-08-17 — *"Requirements are minimum supported and
  recommended… kernels, RAM + VRAM, sm_x, CUDA version, pytorch version… the
  endpoint author already specifies the (GPU, lane) rungs; leave it to them to
  configure, don't automate."*

  **The terms.** `KNOWN_REQUIREMENT_TERMS` grows from `min_sm` alone to
  `min_sm`, `min_vram_gb`, `min_host_ram_gb`, `min_cuda`, `min_torch`, spelled
  compactly as `"sm100+, vram80g, ram64g, cuda12.8+, torch2.9+"`. The bag is
  its own struct (`RequirementTerms`) and `LayoutRequirements` becomes the
  PAIR. A term and the machine fact it is compared against carry the SAME NAME
  (pgw#1314), so evaluating a requirement is a name lookup and never a bespoke
  comparator per term. `kernels` is NAMED AND REFUSED, NOT BUILT: there is no
  runtime kernel-capability probe in this worker, so it would be a floor with
  no fact behind it, and an ignored requirement is one that silently does not
  hold.

  **The two levels.** The COMPACT form stays the MINIMUM, so the fleet's 18
  existing `"sm89+"` / `"sm100+"` declarations keep their meaning AND their
  manifest row byte-for-byte — `{"min_sm": 89}` is still emitted flat, which
  is where th#2030's ingest reads it, so repinning this wheel cannot silently
  drop a floor the hub already enforces. `recommended` is purely additive,
  nests under its own key, and is refused at declaration when it falls below
  the minimum on any term (a recommendation below the floor is a
  contradiction, not a preference). A minimum gates ADMISSION — a config-write
  check on a pick a human is making — and never execution; a recommendation
  gates nothing at all, ever, because the hub learning a monotone buy floor
  from one is exactly th#1720 / th#1867.

  **The FUNCTION scope: `Resources(requires=)`,** same grammar, same terms,
  for code with no contract to hang a requirement on. Not scope creep:
  training-endpoints has ZERO `Slot(...)` model slots (te#209), so its four
  endpoints cannot express a floor any other way. **`compute_capability=` and
  `ram_gb_hint=` FOLD INTO IT and are DELETED** with no alias — each was a
  bespoke axis with its own parser, its own payload key and its own hub
  readers. The sm floor survives verbatim as `min_sm` in tensorhub's BARE
  spelling (89, 100), the same spelling `WorkerResources.gpu_sm` and
  `contractspec.DecodeEntry.MinSM` use; the dotted 8.9 is gone rather than
  kept as a second stored form. `ram_gb_hint`'s misnomer ends with it — a
  field named `_hint` the hub enforced as a pod-create minimum.

  **Host RAM is declarable as `recommended` ONLY** (Paul, 2026-07-11: RunPod
  GPU pods cannot select or guarantee host RAM, so a minimum is unenforceable
  theater and the standing instruction is not to rebuild a boot-time RAM
  gate). ie#492's measured 64 GB ask survives as a recommendation; unmet, it
  is a degrade warning, which is what the offload rungs already do.

  **One compatibility projection, named and owned.** `manifest_dict()` still
  emits `compute_capability`, re-derived from `minimum.min_sm`, so this wheel
  cannot dark an sm floor the hub is enforcing today in the window before
  th#2072 reads `requires` — deleting the emitter before the reader moved is
  how that floor vanished silently the first time (th#1155 x6, te#125). Two
  projections are deliberately NOT made: `min_host_ram_gb` does not become the
  builder's `ram_gb` pod-create minimum, and `min_vram_gb` does not become its
  `min_vram_gb` buy filter — arming the lane VRAM floor is th#2073's, in one
  change with the runpod fail-open closed.

  `scripts/lint_layout_declarations.py` reviews the new form at both scopes:
  a requirement is a compact string literal or a `LayoutRequirements(
  minimum=…, recommended=…)` call with string-literal levels, because a
  computed requirement is unreviewable exactly where it matters.

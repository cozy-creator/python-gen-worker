- **`uv sync --locked` failed on every cold environment, and the message blamed the wrong thing.**
  CI's first step died with `Hash mismatch for torch==2.13.0+cu130`, computing
  `95bdbad2…` against three expected hashes — which read as "the cu130 index republished the
  wheel". It did not: `95bdbad2…` is the **cp313** x86_64 wheel, byte-identical to what the index
  has served since 2026-07-08, and the cp312 wheel still hashes to exactly the `8db7338e…` the lock
  records. The index publishes `#sha256=` for torch 2.13.0+cu130's cp310/311/312 rows and **not**
  for cp313/cp314/cp315, so uv.lock stores those rows hashless — and `uv sync --locked` checks a
  downloaded wheel against the hashes it holds for the **version**, not for the file. `.python-version`
  had been deleted (incidentally, in a Feb 2026 rename commit), so uv picked whatever interpreter the
  machine offered: 3.12 on a GitHub runner, 3.13 on any box with 3.13 installed. CI was green by
  accident of the runner image, and every fresh worktree was red. `.python-version` is restored to
  `3.12` — now the only spelling of the fact, with all four workflows moved to a bare
  `uv python install` — and `scripts/lint_locked_interpreter.py` refuses, stdlib-only and ahead of
  uv itself, any tree that pins no interpreter or pins one whose Linux wheels uv.lock does not hash.
  It is discriminating on the real tree, not merely quiet: green at 3.12, red at 3.13 naming
  `torch-2.13.0+cu130-cp313-cp313-manylinux_2_28_x86_64.whl`.

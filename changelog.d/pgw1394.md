- **Every v2 endpoint was UNPUBLISHABLE, and the reason was one manifest field carrying the wrong
  vocabulary.** `discovery/entrypoints_v2._model_slot` emitted a model class's SERVING LANES as the
  slot's `layouts`, and keyed `layout_requirements` by the same stamps. Those are the hub's
  ARTIFACT-layout fields — the quant x topology axes registered in `internal/tensorlayout` — and
  `slot_layouts.go` resolves every handle in them to a descriptor digest so the conversion ladder
  can walk `(axis, from, to)` edges. A serving lane is not a point on either axis, so the publish
  was refused:

  ```
  slot_layout_demand_invalid: artifact_contract_unregistered — function "generate"
  slot "model" path "pipeline" demands "sdxl.diffusers-bf16@1"
  ```

  after a full image build and a 5m29s registry push. Measured on the standing master stack against
  `serverless-endpoints` sdxl 0.3.1 at `edba7a1`; minimax-h3 emitted the identical shape
  (`layouts={"pipeline": ["minimax.h3-dit-diffusers@1"]}`) and would have failed the same way.

  **The two repos were never drifted.** `models/tensor_layout_contract.py` already lists exactly the
  handles the hub registers — `plain.bf16@1`, `cozy.fp8-rowwise@1`, `nunchaku.v1@1`,
  `cozy.svdq-nvfp4-lr8@1`, `bfl.nvfp4-preswizzled@1`, `hf.fp8-blockwise@1` plus the seven topologies
  — a set-equality with what the hub enumerated in its own refusal. It was the wrong vocabulary in
  the right field, which is why registering the lane handles hub-side would have been the wrong
  fix: it would teach the ladder to "convert" to something that is not an artifact layout.

  Introduced by `9841d3ac` (pgw#1387, "the entrypoints[] block matches the hub's decode"), so every
  pin at or after it carried the defect — including both live endpoint pins, `f6917d52` and
  `8dbce771`.

- **The `requires=` floor now travels where a floor belongs: `functions[].resources.requires`.** The
  artifact-layout fields existed only to CARRY that floor — the hub refuses a `layout_requirements`
  handle the slot does not accept, so the accepted set was manufactured to make the floor legal, out
  of the one vocabulary that could not be. `resources.requires` is THE FUNCTION SCOPE of the same
  requirement vocabulary, parsed by the SAME `machinereq` parser, so the terms cross the wire
  unchanged and only the field is corrected.

  Where a function serves several lanes the floors fold to the STRICTEST, not the last — a function
  is placed on one machine before anything knows which lane it will serve, and collapsing by taking
  the last would be a silent under-declaration the buy path cannot detect. The fold asks
  `term_meets`, the vocabulary's single comparator at both ends, rather than a local `max()`: a
  naive numeric max picks `min_cuda 12.9` over `12.10`.

- **A v2 entrypoint with a model slot now declares `gpu: true`, which it never did.** Its only
  machine signal used to be the `layout_requirements` the hub was refusing, so a v2 release reached
  the buy path with no accelerator declared at all — the
  `[runpod] no GPU constraint declared; buying with NO VRAM bound` branch. A slotless entrypoint
  still emits nothing: an empty `resources` block is an explicit CPU declaration on the hub side,
  so absence had to stay absence rather than become `{}`.

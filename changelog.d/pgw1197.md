- **pgw#1197 (P0, fixes a defect shipped in 0.113.0): the discovery stub satisfied a GUARDED optional
  import, so torch concluded an absent triton was installed and then died touching it.** Measured on
  a real fleet1130 conversion build (CPU profile): `conversion.quant.vendored_h3` → diffusers'
  `PeftAdapterMixin` → `peft_utils` → `torch_utils` → `torch._dynamo` → build dead.

  **The root cause is the IMPORT, not the exception type.** `torch.utils._triton.has_triton_package()`
  is exactly `try: import triton / return True / except ImportError: return False`. Our stub made
  that import SUCCEED, so it answered **True** with triton absent; `torch/_dynamo/utils.py:2874-2877`
  then ran `common_constant_types.add(triton.language.dtype)` — **which is not inside any `try`** —
  and every module reaching `torch._dynamo` died.

  **The fix: a root that third-party code PROBES by import is never stubbed.** `triton`, `xformers`,
  `flash_attn` and `bitsandbytes` leave `DEFAULT_HEAVY_ROOTS` for the new `NEVER_STUB` map, each with
  its reason attached. No endpoint imports them at module scope — they are reached inside kernels and
  handlers — so stubbing them bought nothing while turning "absent" into "present but landmined". The
  per-project extension point now refuses them too, loudly on stderr, because silently honouring one
  would reintroduce this with no trace in the build log. This is the module docstring's own
  `find_spec` rationale applied to the *other* availability-probe idiom: we already refused to fool
  `find_spec`, and were fooling `import` at the same time.

  **The filed fix direction — "raise an `ImportError` subclass" — is wrong twice over, and both arms
  are now pinned by tests.** `HeavyDepStubError` cannot be both an `AttributeError` and an
  `ImportError`: CPython refuses the dual base with *"multiple bases have instance lay-out
  conflict"*. And dropping the `AttributeError` base **breaks `from torch import nn`** — the import
  machinery's submodule fallback catches `AttributeError` on `torch.__path__` — which is the very
  import the stub exists to make free. It would not have fixed the reported chain either, since the
  fatal touch has no guard around it.

  **No second fleet re-mint.** `toolchain_digest()`, `declaration_digest()` and `loaded_libs_digest()`
  are byte-identical before and after, measured on torch 2.13.0+cpu with triton installed so every
  component is populated (`declaration c757897a48482e33`, `loaded_libs 81e526e82b04c440`). A standing
  test pins that this wheel's own source is not a toolchain-axis input.

  training-endpoints' `f5f2639f` workaround (installing the real triton wheel into conversion's CPU
  profile) can be reverted once this ships.

- **The `compat-*` intent a `RunJob` had to fabricate is GONE for JOBS: a job
  dispatch reports against the HUB's carrier** (pgw#1307 arm (8), unblocked by
  th#2052). The arm's blocker was quoted from the code it wanted to delete —
  `ensure_local_intent` existed because *"the wire lacks a job intent
  kind/owner field"*. The wire grew it: `DesiredIntentKind
  .DESIRED_INTENT_KIND_RUN_JOB` plus `RunJob.intent_kind|intent_id|goal_id|
  phase_budget_s` (fields 18-21, additive) are vendored into
  `proto/worker_scheduler.proto` byte-identically to tensorhub `2c6f75271`, and
  `Executor._dispatch_intent` adopts `job-<job-id>-<attempt>` under goal
  `job-<job-id>` instead of hashing an id the hub has never heard of. Measured
  on pristine `origin/master` `88e0a742` before the cut: one real job dispatch
  produced `compat-job-e5fe2afb78a8def7d1cdda81`. After: the hub's own id, and
  zero `compat-` intents in the registry.
- **The FRAME routes, not the name.** pgw#1324 had to resolve
  `RunJob.function_name` against both the endpoint and the job inventory
  because a dispatch carried a name and nothing else. `intent_kind` now picks
  the table, so a dispatch that crosses — a job name asked for as an endpoint,
  or the reverse — is refused with a message that SAYS which way it crossed,
  instead of being told to rename a name that is perfectly correct.
- **`phase_budget_s`, when the dispatch states one, replaces the wheel's
  compiled `DEFAULT_PHASE_BUDGET_S`.** One question — "is this job advancing?"
  — had two numbers: the hub's liveness sweep read the operator's
  `jobs.progress_budget_s` and the worker read whatever it was built with. The
  hub remains the kill authority; the two ends now read one value.
- **Two arms deliberately KEPT, each with its own reason recorded rather than
  inherited.** (1) `ensure_local_intent` survives for `setup` / `materialize`,
  their single-flight waiters, and the SERVED-REQUEST half of the dispatch
  head: a served request is not an intent on this protocol and never was — it
  is what an intent gets BLOCKED on (`IntentState.blocker_request`) — so
  th#2052 gave a carrier to jobs only and that half stays. (2)
  `_WAITING_DEADLINE_FALLBACK_MS`, re-read against `phase_budget_s` as arm (8)
  asked: it fills a REQUIRED field on any blockerless WAITING report, whoever
  authored the intent, while `phase_budget_s` bounds one job's position
  advance. Deleting it with the minter would have made every blockerless
  WAITING report invalid, including hub-authored ones.
- **RULING, recorded because the old justification is now false:** the boot
  refusal of a name declared as BOTH an `@endpoint` and a `@job` is KEPT, on a
  new reason. It used to say a dispatch "names a function and nothing else"; it
  now stays because the published manifest, the catalog, every submit surface
  and `gen-worker job <name>` all resolve by name alone. Publish hygiene, not a
  dispatch-resolution necessity.
- A RUN_JOB frame that carries no carrier is REFUSED
  (`adopt_dispatch_intent` raises) rather than papered over with an invented
  id, and an adopted id is never renamed on a redelivery — the compat minter's
  `-N` suffix was legitimate only because the id was its own to choose.

### Added

- **pgw#1294 ⇄ th#2049 (JOBS program): `@job` — run-once submitted functions, with a body that is PORTABLE to `@endpoint`.** A job is an arbitrary one-off long-running execution for one user (a quantization, a fine-tune, a dataset bake): submitted rather than invoked, run once on a pod with its own lifecycle, billed per GPU-second. `@job(resources=Resources(gpu=True), env=("HF_TOKEN",), resumable=True)` decorates a MODULE-LEVEL function taking `(ctx: JobContext, payload: Struct) -> Struct` — the same contract `@endpoint` functions take, so a job promotes to a bounded-recipe serverless endpoint by wrapping the same body and pricing it, with zero body edits. A class, a method, a generator, the wrong arity or a non-`Struct` payload/result is a typed refusal at DECORATION naming the rule; there is no `setup()`, because the lifecycle is a fresh child per job on the existing parent-stream/child-CUDA split and nothing survives in-process between jobs by contract. New: `gen_worker.job`, `gen_worker.api.jobs.JobDecl`, `gen_worker.registry.JobSpec` / `extract_job_spec` / `collect_jobs`, `gen_worker.discovery.walk.find_jobs`.

- **`gen_worker.jobs`: the run-once harness and this wheel's dispatch contract.** `JobDispatch` / `JobOutcome` / `execute_job(dispatch, jobs=…, ctx=…)` — resolve the name against this release, decode the payload against the PUBLISHED schema, arm the progress watch, call the body once, encode the result. Transport-neutral on purpose: `RunJob.function_name` already routes by name and `JobResult` is already the result envelope, so v1 needs no new proto message and th#2050's scheduler head fills in these two structs rather than a second execution path. `JobOutcome.recycle_child` states the run-once lifecycle as data rather than as a comment. A body that raises is TERMINAL and the typed exception rides `error_type`, so the scheduler's infra-vs-body retry split is made from a type.

- **`gen-worker job run <name> --payload file.json` / `gen-worker job list`.** The author dev loop, hub-less: the real registry walk, the real schema decode, the real `execute_job` harness and a real `JobContext` with only the hub-backed accessors stubbed. GPU jobs are refused on a control box by declaration, before anything loads.

- **`ctx.progress` liveness is POSITION ADVANCE, never pulse and never duration.** `ctx.progress(position=…, total=…, phase=…)` is the job spelling of the existing `ctx.progress(fraction, stage, step=…, total=…)`; both feed one event and one monotonic position ledger, which is what makes a body portable between the decorators unchanged. A position that goes BACKWARDS inside a phase raises `NonMonotonicProgressError` — a stall detector reads this number, and an instrument that lies is worse than none. The positional job form is REFUSED rather than reinterpreted by argument type. **pgw#1287's class now cannot bank as a success**: `ProgressWatch` fails a run whose phase reported nothing inside its budget with a typed `JobProgressStalledError`, even if the body returns normally afterwards — the exact shape th#2014 measured, where a pod downloading correctly reported `0 / total` for eleven minutes and was condemned. `ctx.metric({...}, step=, total=)` generalizes `training_metric` onto `request.metric`, same throttle, emitting one `{name, value, step, total, phase}` row per named scalar — the shape th#2050's landed `forkJobProgress` parses.

### Changed

- **The hub-write declaration is ONE surface for BOTH decorators: `publishes=True` on `@endpoint` and on `@job`.** Paul's tensor-emission ruling (2026-08-16) — *"serverless endpoints must ALSO be able to emit tensors / write to the hub — declared in their interface"* — is what makes a serverless-LoRA trainer possible. It says MAY write; the request still says WHERE. It rides BOTH manifest row shapes (`functions[].publishes` and `jobs[].publishes`), always emitted and never omit-when-false, because the hub mints the worker-capability write grant off it and "absent" must mean "wheel too old to have the concept" rather than "declared false". SDK side, `save_checkpoint` / `open_checkpoint_stream` / `convert.publish_flavors` raise `PublishNotDeclaredError` for undeclared code, before a byte moves — the hub never minted the grant, so this is that refusal arriving at the call site instead of after an upload. TRANSITIONAL: the producer KINDS (`conversion`/`training`/`dataset`) still imply write authority for the un-migrated fleet and every such admission CONFESSES via `ctx.log`; th#2052 deletes that arm and the declaration becomes the only justification.

- **`ConversionContext` + `TrainingContext` + `DatasetContext` MERGED into `JobContext`**, which is a strict superset of the producer-endpoint context surface under the same names — that superset property is what portability rests on, and it is tested by registering ONE body under both decorators and running it green under both harnesses. The three old names are thin aliases and die at th#2052; nothing new should reference them.

- **The manifest carries a `jobs:` block beside `functions:`** (name, python_name, module, input/output schema + sha256, resources, env, resumable, visibility, publishes, source_file and captured source text). One package may carry both; publish once, submit as needed, and a release with jobs and zero functions is legal. `source_file` is a POINTER into the release tarball, never a copy of the bytes — reconciled to th#2049's landed correction 6, since the tarball already serves per-file views and a captured `source` text field would be a second copy that can only drift. The block is sorted by name: the manifest is a published artifact and must be byte-stable across runs.

- **Wire shapes reconciled to the LANDED hub halves** (th#2049 `a4ebb8597`, th#2050 PR #1334), which landed while this was in CI and are the producer of the contract. `ctx.progress` now emits `step` for EVERY position, not only integral ones: `runtimestore.ParseRequestProgressPayload` reads `step`/`stage`/`total` and nothing else, so a position that only reached the `position` key would have been invisible to the liveness sweep that condemns the pod — the precise way pgw#1287 killed pods that were working. th#2050's correction 7 independently adopted this lane's decision that a job rides `RunJob` unchanged (`request_id` = job uuid, `function_name` = job name), so no proto message was needed on either side.

- **Positions ride the CTX-EVENT channel, never the output channel.** th#2050 landed `JobProgress` as a streaming OUTPUT chunk and put job liveness on the ctx-event envelope instead — `forkJobProgress` parses only `application/x-request-event+json` frames and drops raw output chunks — so a position emitted on the output channel would be invisible to the freshness window and to th#2014's brake, indistinguishable from a pod doing nothing. Asserted both ways, and a job structurally has no output-chunk path at all: a generator body is refused at decoration.

- **`execute_job` STAMPS the job's `publishes` declaration onto its context**, so a dispatch head cannot forget it. The `JobSpec` is the one home for the declaration (it comes from the decorator and rides the manifest row the hub mints the write grant off); the context flag is a projection. A head that built the context without it would hand a job a perfectly valid capability token and then have the SDK refuse the job's own publish — a wiring bug that reads as a broken feature. The opposite direction is a typed refusal rather than a silent downgrade: a caller cannot grant publish authority for a job whose release never declared it, because the hub minted no grant for it.

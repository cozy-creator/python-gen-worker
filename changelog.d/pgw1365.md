- **The publish path chunks on the Rust planner's grid.** `hubio/client.py::publish_v2` admits
  every file it publishes through `LocalCAS.ingest_file`, which planned with the greedy
  small-tensor packer upstream deleted at tensorfs `00c57c1` ("one chunker — the legacy Python data
  plane is gone") — so the mixed-CAS ruling's "one chunker (the Rust planner is canonical)" was
  true inside tensorfs and false in the fleet, and every fleet upload cut its objects where nothing
  else in the system cuts them. Measured against upstream's released conformance corpus
  (`spec/v1/planner-vectors`), 3 of 12 cases disagreed: a safetensors pair packed a 3-byte and a
  5-byte tensor into one object where the planner emits two, and BOTH GGUF cases were planned as
  raw blobs because the retired module had no GGUF planner at all — which silently undid pgw#1344,
  whose whole point was composing GGUFs on the planner grid. The vendored `chunking.py` is replaced
  by `planner.py`, a pure-Python port of `crates/tensorfs-core/src/planner/{mod,safetensors,gguf}.rs`
  (the pgw#1310 precedent: the compiled extension cannot ride a source-vendored wheel), declared in
  `VENDORED.toml` and pinned to the vendored corpus object-for-object and digest-for-digest. A
  one-tensor edit in a 16-tensor checkpoint now moves 1,024 bytes instead of the whole 16 KiB data
  section. One deviation remains and is tested by name: a blob above 64 MiB is still cut on the
  fixed grid, because tensorhub's publish-v2 lane promotes with a single PUT (pgw#1366).

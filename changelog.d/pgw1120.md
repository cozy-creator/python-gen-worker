- **pgw#1120: a rig now proves the HOST can run the fleet line, not just that the
  wheel says so.** `rigcheck` compared version strings, which is exactly what a
  too-old RunPod host does not fail: on driver `570.211.01` (CUDA 12.8) a
  `torch 2.13.0+cu130` reports every version correctly, `rigcheck` printed *"on
  the fleet line"*, and the first ALLOCATION died ~20 minutes later with "driver
  too old" — after the weight fetch, reading as a torch bug. Two lanes hit it the
  same night; pgw#1043's fleet-line re-cell was abandoned on it. RunPod's driver
  is per-host (five consecutive SECURE H100s drew 570.211.01; US-GA-2 drew
  580.159.04 two days earlier), so this is not a one-off.

  New `gen_worker.rigboot` is the bring-up gate: it probes `nvidia-smi` with no
  torch and no install (so it runs as the FIRST command on a bare pod, before any
  multi-GB fetch), decides against NVIDIA's minimum-driver table, and proves
  usability with a real allocation in a fresh interpreter. When the driver is too
  old it installs NVIDIA's forward-compat libcuda and re-verifies — the fleet base
  image carries no NVIDIA apt repo and no curl, so the `.deb` is fetched with the
  stdlib and `dpkg`'d — and it reports which of three paths it took (`native` /
  `compat` / `reroll`). Exit 91 means re-roll the host. Proven on a real
  570.211.01 H100: repaired to `cuda_available`, sm9.0, 79.19 GiB, in 3.5 minutes.

  `rigcheck.assert_fleet_line` now performs the same real allocation and raises
  the new `CudaUnusable` (a `FleetLineMismatch` subclass; CLI exit 91, not 90)
  when a card is present and cannot be allocated on. Its message says *repair or
  re-roll the host*, never *rebuild the environment* — the wrong instruction there
  costs another pod. The driver-vs-CUDA comparison is version-TUPLE based: as
  floats `580.159 < 580.65` and the obvious implementation rejects the exact host
  that works. Guidance: `research/RIG-ENV.md` §3c.
